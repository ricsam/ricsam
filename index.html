01 / SELECTED SYSTEMS

How the current work fits together.

Four groups of projects, ordered from the work I am doing now and described by the boundaries and data flows between them.

SYSTEM 01

Agents / execution

Research, code execution, and shell tools with explicit boundaries.

Agentic Web Research searches through a bundled SearXNG instance, renders selected pages in Playwright, converts them to Markdown, and lets a model decide what to inspect next. An authenticated REST API streams typed progress events while URL checks reject private and internal hosts. Isolate runs JavaScript and TypeScript in V8 contexts whose files, modules, network access, browser sessions, and host functions are supplied as bindings. Shell DSL adds pipes, redirects, scripts, and a virtual filesystem using only commands registered by the host process.

  • research
  • isolate
  • shell-dsl

Each capability is passed in; none is assumed.

SYSTEM 02

Web / contracts

One contract connects the server, client, and documentation.

Richie RPC defines requests and responses with Zod, validates them on both sides of a Bun API, and derives typed fetch clients, OpenAPI, React Query options, NDJSON streams, SSE, and WebSocket messages. Richie Router scans route files and generates two different artifacts: a client route tree that imports React modules, and a server-safe manifest that contains only route structure and metadata. The backend can serve the SPA and resolve head tags without executing frontend code.

  • richie-rpc
  • richie-router
  • Bun + React

Shared types cross the boundary; frontend modules do not.

SYSTEM 03

Data / interaction

Rendering, interaction, and workbook state are separate layers.

React TanStack Table UI turns TanStack Table state into virtualized rows and columns, with presentation supplied by interchangeable skins. Selection Manager owns rectangular and multi-range selection, keyboard movement, editing, fill handles, merged cells, and TSV clipboard operations independently of the table renderer. Formula Engine stores workbooks as sparse maps, translates A1 addresses, manages sheets and named expressions, and is where parsing, dependencies, and evaluation are being developed.

  • rendering
  • interaction
  • workbook state

The UI can change without replacing the data model.

SYSTEM 04

Files / scheduled work

The same filesystem interface can back local and remote work.

Nafs presents a subset of Node’s filesystem API over memory, local disk, S3, or an Enstore server. Enstore exposes streamed file operations over HTTP with users, roles, a CLI, and an fs-style client. Enschedule stores schedules and runs in PostgreSQL; workers register jobs with schemas, claim work, and publish status and logs to the dashboard. Nafs lets those logs move between local and remote storage without changing the worker-facing API.

  • enstore
  • nafs
  • enschedule

Storage is selected at the boundary, not inside the job.

02 / WORKING BACKWARDS

The path to the current systems.

The recent projects share code and architectural choices, so they make more sense as a sequence than as a repository list. Starting from now, this is how the layers emerged.

  1. Now

    Constrained runtimes for agentic software.

    Current work combines web research, browser automation, model calls, V8 isolation, and an in-process shell. The focus is on how agents receive tools, how work is cancelled, and how nested execution remains subject to host-defined limits.

  2. 2025—26

    Typed application infrastructure.

    Building applications with Bun and React led to Richie RPC and Richie Router. In parallel, table work split into renderer, selection, and workbook packages so each layer could evolve and be tested independently.

  3. 2022—25

    Jobs, files, and operational state.

    Enschedule grew from job registration and cron execution into a PostgreSQL-backed worker system with a dashboard and typed API. Enstore and Nafs supplied a consistent route for files and logs across local development and deployed workers.

  4. 2019—22

    Libraries with narrow responsibilities.

    React component libraries, command-line tools, and the first Nafs implementation established the pattern used in the newer work: keep stateful mechanics in a focused package and let applications decide how they are presented and deployed.

“Capability should be explicit, state should be inspectable, and each layer should remain useful on its own.”
